Browsing recipes

The explorer

Modules are directories, recipes are files, aliases point at what they alias. The tree is the justfile, including everything mod pulls in.

Groups

A recipe carrying [group('x')] is filed under a collapsible folder inside its module — beside the modules, never instead of them, which is what just --list does too.

just-tui — groups
│▾ project/                     ← the module
││ ▸ tools/                     ← a real `mod`, untouched
││ • default ★  Show every rec… ← ungrouped recipes stay put, above the folders
││ ▾ build  2 recipes           ← [group('build')]
││ │ • compile  Build the binary
││ │ • release  Optimised build
││ ▾ data  2 recipes            ← [group('data')]
││ │ • fetch  Download the inputs
││ │ • clean  Drop the cache

The layer appears only where it divides something: a module whose recipes fall into two or more buckets, counting ungrouped as one. A module with a single group, or none, is left alone. m folds the layer away and back.

Groups are display only. A namepath never contains one, so running, submitting and config scopes are unaffected.

Arguments

Enter on a recipe with parameters opens a form in the middle of the screen, one row per parameter, with each default shown beside its row. Leave a row empty to keep its default; Enter runs, Esc cancels. What you typed is remembered per recipe in .just-tui-run-args, so the form opens the way you left it. a opens the form for any recipe — one without parameters gets a single free row for whatever should follow its name. Try it in the demo on simulate-reads.

Variables

V lists the variables of the module the selection is in. Enter on one opens a full-screen directory explorer at the path it currently names — the nearest directory that exists, relative values taken from where the module's recipes run. Walk with ⏎ and ←, press space to choose what is highlighted or c for the directory you are in; . shows hidden entries, ~ goes home. In the list, e types a value instead and d drops an override.

The justfile is never touched. A chosen value is an override, remembered per project in .just-tui-overrides and passed to just on every run and submission exactly as you would type it: just --set sub::out /scratch/run1 sub::align.

If you use qwe for directory bookmarks, the explorer shows them in a column of their own — ⇥ switches to it — read from ~/.qwe.data.

Search

/ matches recipe names as a fuzzy subsequence and documentation literally, and highlights the characters it matched. It matches the file name too, so /git narrows to a global git.just library and /gitlog finds one recipe inside it. q clears the search first and quits second.

Global recipes

just-tui's global recipes are just's own: whatever just --global-justfile (just -g) sees, usually ~/.config/just/justfile. They appear as one more root, marked ⌂, below the project, and run as just --global-justfile <recipe> from the directory you started in — exactly what typing just -g there would do. Anything you can see under ⌂ you can also run from a shell. The global root starts collapsed, and just-tui still opens if there is no justfile here at all.

Libraries are modules of that justfile:

# ~/.config/just/justfile
mod git                       # ~/.config/just/git.just

# ~/.config/just/git.just
[no-cd]
log:
    git log --oneline -20
Mark global recipes [no-cd], or just runs them in ~/.config/just rather than in the repository you are standing in. just-tui does not change that: it runs them the way just -g does.

What just-tui remembers about global recipes lives in ~/.just-tui, not in the directory you ran them from: the last Slurm settings, the last run arguments, the submission history and the job logs. A global recipe run in twenty directories leaves no files behind in any of them. Hand-written .just-tui-cluster-config files still apply as usual.
